# Password Health Report

The per-Vault Password Health report (issue #64) analyses every in-scope Entry's password and surfaces four finding kinds — Very Weak, Weak, Reused, Expired — to three UI surfaces: a dedicated `/dashboard/security/$dbId` route, a warning icon in `EntryListItem`, and a count badge on the sidebar "Security" item. Analysis runs in Rust against cleartext that never crosses IPC, using the `zxcvbn` crate for pattern/dictionary detection and a per-analysis keyed BLAKE3 hash for reuse grouping. It is triggered automatically ~1s after a Vault unlocks, streams per-Entry findings to the frontend as Tauri events so the icons populate progressively, caches per-Vault keyed on a generation counter bumped by `Vault::mark_modified()`, and is cancelled when the Vault locks.

## Considered Options

- **Frontend-side analysis reusing `@zxcvbn-ts`** — rejected. Would require shipping every Entry's cleartext password over IPC, contradicting the "minimal data in list views, no passwords to frontend unnecessarily" rule. The live strength meter on the password generator stays in JS because it scores one transient string the user is typing — it doesn't need backend access. The two are intentionally separate.
- **Cross-Vault reuse detection** — rejected. Locked Vaults can't participate, so the report would be non-deterministic depending on which Vaults the user happened to unlock. Reuse across Vaults isn't unambiguously a security finding either (compartmentalization is a legitimate use of two Vaults). Per-Vault matches the rest of the model (Audit Log, Database Config).
- **"Old password" check (>= 6 months since last modification)** — rejected. NIST SP 800-63B-3 §5.1.1.2 explicitly recommends against periodic rotation when there's no evidence of compromise; the empirical justification is that forced rotation produces weaker, more-predictable passwords. The issue itself asked us to research this; the answer is "don't do it."
- **Breach-corpus / HIBP check ("Compromised" in the `EntryListItem` placeholder comment)** — deferred to a separate feature. It's the only check that touches the network, the privacy model deserves its own ADR (same shape of decision as third-party favicon fallback), and the issue's check table doesn't actually include it.
- **Weighted finding-deficit score** (start at 100, subtract per-finding weights) — rejected. Requires us to defend magic weights, double-counts Entries with multiple findings, and produces non-monotonic deltas on remediation. The healthy-entry-ratio formula `100 × healthy / total` is well-defined, has no knobs, and moves predictably as the user fixes things.
- **Lazy analysis on first navigation to the report** — rejected. The warning icons and sidebar badge exist precisely so the user notices health passively, without having to ask. Lazy analysis leaves both surfaces blank on the first visit.
- **Synchronous IPC with no progress events** — rejected. zxcvbn on a 1,000-Entry Vault is several seconds of CPU; freezing the IPC thread for that interval is unacceptable. The async-with-events pattern is already established by the Audit Log tail.

## Consequences

- The JS-side entropy strength meter and the Rust-side zxcvbn classifier will occasionally disagree on borderline passwords. The generator may say "Fair" for an 8-character random string that the report leaves un-flagged. This is acceptable — they serve different purposes (live feedback vs. periodic audit) — and could be tightened later by porting the live meter to call a backend command.
- An Entry that is both Very Weak and Reused produces two findings, not one merged finding. The score formula treats it as one un-healthy Entry. The UI shows both finding rows because the remediation differs (regenerate this Entry vs. regenerate every Entry in the reuse group).
- Lock-then-unlock drops the cache and re-runs analysis. We are not persisting the report across lock cycles — doing so would encode finding distribution on disk while the Vault is locked, which has a privacy cost we judged not worth the CPU savings.
- Adding the "Old" check back, or adding HIBP breach-checking, are both forward-compatible: they slot in as new `Password Health Finding Kind` variants and don't require revisiting any of the architectural decisions above.
